# METNMAT platform security audit — 2026-09-17

**Scope:** the four applications (website, CMS, chatbot, Command Center), the AWS account
`976134557584` and the shared production host `i-0b446863ec28109b0`.
**Method:** read-only code review of all four codebases (two by cloning `METNMAT-chatbot`
and `Metnmat_Dashboard` locally), read-only AWS API inventory, read-only host inspection
over SSM, light manual probes of the public endpoints, and production-dependency audits.
No configuration was changed during the audit phase. Secret values were never read;
key names and lengths only.
**Threat model:** anonymous internet user; a registered customer attacking another;
a chat visitor driving the LLM; a low-privilege staff account; the holder of one
leaked secret; a compromised app process on the host; the supply chain.
**Severity:** P0 exploitable now with high impact · P1 exploitable with a precondition,
or a high-impact misconfiguration · P2 defence in depth · P3 hygiene.

This is a dated snapshot. The "Status" column is updated as fixes land; the
"Already good" section exists so the next audit does not re-check solved ground.

## 2. AWS account and host

### AWS-1 (P1) The compromised host's instance role is still an administrator
`metnmat-dashboard-role` (instance profile `metnmat-dashboard-profile`, attached to the
stopped instance `i-0b7f49ca3e9852d4b`) carries an inline statement `Action: *` on
`Resource: *`, plus `secretsmanager:GetSecretValue` on `metnmat/prod/*` and
`metnmat/chatbot/*`, `ListSecrets *`, read/write on both media buckets, and Bedrock. The
role was last used 2026-09-16. Anyone or anything able to start that instance, or to
attach that profile to another instance, inherits full control of the account, and the
role is exactly what the attacker had in August.
**Fix (owner, IAM console):** detach the instance profile from `i-0b7f49ca3e9852d4b`,
then delete the role and profile (keep the forensic EBS snapshot). If the instance must
stay startable for forensics, replace the inline policy with `AmazonSSMManagedInstanceCore`
only.

### AWS-2 (P1) Legacy secrets still stored
31 secrets under `metnmat/prod/*` and `metnmat/chatbot/*` remain (last changed
2026-08-11 to 2026-09-04): `INTERNAL_API_KEY`, `PAYLOAD_SECRET`, `JWT_SECRET`,
`RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `GOOGLE_CLIENT_SECRET`,
`RESEND_API_KEY`, `MONGODB_URI`, `OPENAI_API_KEY`, `PINECONE_API_KEY` and more. Every
value that lived on the old host is treated as burned; some of these may still be live at
the provider (Razorpay, Google, Resend). They cost about $12/month and widen what any
admin credential or AWS-1 can read.
**Fix (owner):** confirm each live value exists in the per-app secrets
(`metnmat/{web,cms,chat,cc}/env`), then delete the legacy secrets with the default
7-day recovery window.

### AWS-3 (P1) Root used for daily operations
GuardDuty recorded `Policy:IAMUser/RootCredentialUsage` twice today (`ListAccessKeys`
11:49 UTC, `PutSecretValue` 11:55 UTC): the owner's console work on secrets was done as
root. Root has no permission boundary, cannot be scoped, and its session cannot be
revoked short of a password reset.
**Fix (owner):** create a personal IAM user (or IAM Identity Center user) with MFA and
AdministratorAccess for daily work; keep root for billing and account settings only,
with its MFA device stored offline.

### AWS-4 (P1) Long-lived administrator access key on a laptop
`metnmat-migration` (AdministratorAccess, no MFA) has an active access key created
2026-08-12 that is used from this laptop for SSM and Secrets Manager reads, plus an
inactive key from the same date. A stolen laptop or a malicious npm package on it is an
account takeover.
**Fix (owner):** delete the inactive key; replace the active key with short-lived
credentials (an assumable role with an MFA condition, or Identity Center); scope the
permissions to what operations actually need (SSM SendCommand on the two instances,
Secrets Manager describe, read-only elsewhere).

### AWS-5 (P2) Legacy deploy role with broad reach
`metnmat-dashboard-deploy` (OIDC, trusted for `Metnmat_Dashboard:master`) may
`ssm:SendCommand` on the old host and the worker and `s3:PutObject` on the whole
artifact bucket. The Command Center's `deploy-cc.yml` already uses
`metnmat-github-deploy`; only `deploy-whatsapp-worker.yml` still assumes this role.
**Fix (owner):** remove the old instance id from the policy and narrow S3 to a
`worker/*` prefix, or migrate the worker workflow to the shared role and delete this one.

### AWS-6 / AWS-7 (P3) Leftovers
Worker `i-001a2ec37cab94a96`: security group `launch-wizard-1` opens 22/tcp from
`103.50.83.74/32` (SSM is available; remove the rule), root volume unencrypted. Roles
`metnmat-ecs-execution`, `metnmat-task-{chatbot,dashboard,website}` are unused since
the ECS path was deleted. Bucket `metnmat-deploy-artifacts-website-…-an` is empty with
versioning on and no lifecycle. No account password policy exists (no console users
today, so no exposure).

### What is right on the account and host (verified)
- Production security group: 80 and 443 only. Quarantine group: no inbound.
- Production instance role `metnmat-prod-host-role`: read four secrets, read artifacts,
  `PutMetricData`; nothing else. Worker role: SSM parameter read only.
- Deploy role `metnmat-github-deploy`: trust limited to the three repos' default
  branches; S3 write limited to per-app prefixes (bootstrap prefix added today).
- IMDSv2 required on every instance; on the production host the hop limit is 1 and
  nftables drops IMDS for every uid but root (counter shows it working).
- All buckets block public access except the Command Center media bucket, which is
  public-read by design; every bucket is SSE encrypted.
- CloudTrail: multi-region, log-file validation on, delivering. GuardDuty enabled,
  15-minute publishing.
- Host: only Caddy listens publicly; the website, CMS and Command Center bind loopback;
  every unit scores "OK" on `systemd-analyze security`; sshd masked; automatic security
  updates active with zero pending; secrets exist only in root-only tmpfs; no `.env`
  files, no world-writable files under `/srv`; kernel current.
- Public probes: every CMS collection with PII refuses anonymous reads and writes (403);
  GraphQL disabled (404); the website and Command Center send HSTS, CSP, nosniff,
  frame and referrer headers; the chatbot refuses cross-origin preflights.

## 3. CMS

Fixed and deployed 2026-09-17 (PR #20, `deploy-cms.yml`):

- **CMS-1 (P1) Customer email change kept `emailVerified`.** A registered
  customer could earn `emailVerified` (a password reset proves inbox access),
  then `PATCH /api/customers/<me> {"email":"<guest buyer>"}`, and the account
  page would list that guest buyer's orders, addresses and GST invoices (guest
  orders are matched by verified email). Fixed: `hooks/customer-email-change.ts`
  resets `emailVerified` and bumps `sessionsValidFrom` when a non-staff request
  changes the address. Verified by test; live PII collections still 403.
- **CMS-2 (P1) An admin could seize the super-admin.** `users.update` was
  `isAdmin`, and Payload's auth `password`/`email` have no field-level access, so
  an admin could set the super-admin's password and log in as them, or re-point
  their email to hijack forgot-password. Fixed: `hooks/staff-account-guard.ts`
  refuses any edit of a super-admin by a non-super-admin, and refuses one staff
  member changing another's email or password.
- **CMS-3 (P2) Public enquiry create accepted workflow fields.** An anonymous
  POST could file an RFQ already `won`, with a `quoteAmount`, an owner and staff
  notes. Fixed: `hooks/enquiry-public-create.ts` strips every staff-only field
  and forces `new`/`normal` on a non-staff create.
- **CMS-4 (P2) `enquiry-uploads` create was fully public** at the CMS origin,
  bypassing the website's byte sniffing, size caps and rate limits. Fixed:
  `create: internalOnly` (the website server's key). Verified: anonymous create
  now 403; every website upload path forwards the key.
- **CMS-5 (P3) DPDP requests** could be filed pre-`completed` with a chosen
  reference; now forced to `new` with a minted reference for non-staff.
- **CMS-6 (P3) Headers and cookies.** Auth cookies `secure` outside dev; the
  service now sends HSTS, `nosniff`, `X-Frame-Options`, Referrer-Policy,
  Permissions-Policy and drops `X-Powered-By`. Verified live.
- **CMS-7 (P2) INTERNAL_API_KEY blast radius (open — needs owner decision).**
  `inboundKeyMatches` accepts the shared key wherever a purpose key is checked,
  and several `internalOr*` gates return `true` (full listing). One leaked key
  reads every order, ticket, customer upload, private PDF and blog manuscript.
  The provisioned purpose keys (`CMS_ORDER_WRITE_KEY`, `CMS_TICKET_WRITE_KEY`,
  …) are not set, so the shared key is the live credential for all of them.
  Fix is to provision the purpose keys and stop the shared-key fallback, plus
  return `where` constraints on the reads the website only needs one row from.
  Left for a change window because it is coordinated across both apps' env.
- **CMS-8 (P2/P3, open) Login lockout of the director.** `/api/users/login` is
  unthrottled and Payload locks after 5 failures for 10 minutes, so anyone who
  knows the director's email can keep PIN login locked. Fix at Caddy (rate-limit
  `POST /api/users/login`) or by disabling the public local strategy. Needs a
  host/Caddy change, so owner-side.
- **Role drift (P3, open):** marketing manages tickets (customer PII); every
  staff role reads all invoices; `approvedBy`/`approvedAt` on tasks are
  unguarded under `update: isStaff`. Least-privilege tightening for a later PR.

### INTERNAL_API_KEY blast radius (until CMS-7 is done)
The shared key can: read all orders and update their non-payment fields; create
payment-events; read and write all tickets; read/download all enquiry-uploads
and all private documents (quotation and invoice PDFs); read all shipments;
create notifications and integration-log rows; read product/post drafts; read
all blog submissions and manuscripts. It cannot: read customers, users,
invoices (list), leads, audit-logs or globals, and (because `CMS_OAUTH_KEY` is
set) cannot mint a customer session. `enquiries` is already constrained to one
email. Treat the key as able to read most operational PII, and rotate it on any
suspicion.

## 4. Chatbot

Fixed and deployed 2026-09-17 (PR #6, live, re-verified). Empty-body POSTs to
`/api/webhook/instagram` and `/facebook` returned 200 before the fix; they
return 401 now.

- **CHAT-1 (P1) Meta webhooks failed open.** `verifyMetaSignature` let every
  POST through when the app secret was empty, and the secret fetcher drops the
  placeholder the channels currently hold, so anyone could drive the LLM and
  write into any user id's conversation history. Fixed: reject when the secret
  is empty or a placeholder; the Facebook and Instagram verify handshakes
  require a configured token; `/api/webhook/*` is rate-limited; Instagram and
  Messenger sender ids are namespaced (`ig:`, `fb:`) so they cannot collide
  with a WhatsApp phone.
- **CHAT-2 (P1) Tools trusted a model-supplied identity.** `search-tickets-by-
  user`, `update-user-profile` and `create-issue-ticket` took the customer's
  phone as a tool argument, so a widget visitor typing "my number is +91…"
  could list any customer's tickets, overwrite any profile (and thus that
  customer's next system prompt), or file tickets in their name. Fixed: identity
  comes from the verified session (`requestContext`); a typed number is a
  contact hint only. Verified live: a spoofed-number lookup returns "no tickets
  under your session".
- **CHAT-3 (P2) No message length cap / unbounded steps.** Widget messages now
  capped at 1000 chars (verified: 1500 → 400); the clarify call bounded to 3
  steps. Profile values sanitised before they enter a prompt (`lib/sanitize.ts`).
- **CHAT-4 (P3) Auth hygiene.** Agent key compared in constant time; JWT verify
  pinned to HS256; `ALLOWED_ORIGINS=*` rejected in production; `X-Powered-By`
  removed; nosniff/referrer/frame/permissions headers and HSTS added; `BIND_HOST`
  now binds loopback in production (verified: listens on `127.0.0.1:3002`).
- **CHAT-5 (P3) Dependencies.** `socket.io` removed (unused); `axios`
  1.13.5 → 1.20.0; stale `package-lock.json` removed. `whatsappcloudapi_wrapper`
  still pulls an old `request`/`form-data` chain, reached only by WhatsApp image
  sends (not live); revisit when WhatsApp is enabled.
- **Open (P3):** session token still in the widget query string (also supported
  as a header); PII in log files with no rotation; model-supplied `$regex` in
  the product retriever (small collection). Batched for a later PR.

## 5. Command Center

Fixed 2026-09-17 (PR pending, contained auth changes):

- **CC-1 (P3→) 2FA could be disabled by an env flag in production.**
  `TWO_FACTOR_AUTH_ENABLED=false` removed the second factor anywhere; now forced
  on when `NODE_ENV=production`. A host compromise flipping one env value was
  exactly the risk.
- **CC-2 (P3→) CAPTCHA bypass honoured in production.** `CAPTCHA_BYPASS=true`
  now ignored in production.
- **CC-3 (P2) OTP brute-force via a non-atomic counter.** The verify path read
  `otpAttempts`, compared, then saved `+1`, so parallel guesses all cost one
  attempt. Fixed: a guarded atomic `findOneAndUpdate($inc)` reserves an attempt
  before the compare, and `/api/login/2fa/verify` now throttles per IP and per
  challenge.

- **CC-4 (P1, open — owner) `WHATSAPP_WEB_API_KEY` is owner-tier read of the
  business DB.** `/api/integrations/whatsapp-web/config` discloses the owner
  phone and monitored groups, and `/assistant/debug` takes `senderPhone` from
  the body and resolves owner tier, returning AI answers, tool calls and the
  Mongo query. The worker EC2 holds this key, so a worker compromise is CRM
  exfiltration. Fix (needs worker-contract knowledge to avoid breaking it): the
  debug route must not derive the caller from the body (admin session, or
  remove it); drop `assistantOwnerPhone` from `/config`; split an ingest-only
  key from the assistant key; scope the ack/attachment actions. Left for owner
  review because changing the worker's API contract needs testing against the
  worker.
- **CC-5 (P2, open) Login is a username oracle and a remote lockout.** Distinct
  messages for unknown vs locked vs wrong-password; 5 failures locks until an
  admin unlocks, so any known loginId can be locked by an anonymous script.
  Fix: one uniform message and a time-boxed auto-unlock. Owner review.
- **CC-6 (P2, open) Any authenticated role can list/download the whole media
  library** (`/api/media`, `/api/media/file/[id]` check session only), which
  includes quotation/enquiry/invoice files. Fix: enforce the asset's module.
- **CC-7 (P3, open)** Signed invoice/quotation PDF links live 24h and are
  logged with the signature; company signature/stamp/UPI-QR live in the public
  web root; the `WEBSITE_API_KEY` enquiry/order create mass-assigns `...body`.

The Command Center's strengths (verified): constant-time key compares that fail
closed, prod boot refused without `NEXTAUTH_SECRET`, JWT session re-synced every
60s with an invalidation sentinel, impersonation server-side with no
super-admin targets, an SSRF allow-list, operator/field allow-lists on custom
reports, and no committed secrets.

## 6. Website

### WEB-1 (P2) Ticket numbers are guessable
`apps/website/src/app/api/support/route.ts:79` mints `TKT-<yyyymmdd>-` plus four hex
characters (65,536 values per day). `support/status/route.ts` returns the full ticket
(description, order number, every message) and `support/reply/route.ts` appends messages
when number and email match; the only guard is a per-IP limiter. Anyone who knows a
customer's email can walk a day's numbers from a few addresses.
**Fix:** a suffix with at least 40 bits of randomness (the CMS validator in
`apps/dashboard/src/lib/ticket-number.ts` must accept it), a per-email limiter on the
status and reply routes, and the email moved from the query string to the body.

### WEB-2 to WEB-11 (P3)
Evidence and fixes as listed in the register; details in the audit agent's notes are
summarised here: order email should be forced to the session's email when signed in
(`checkout/create-order/route.ts`); add a per-email limiter to login; bump
`sessionsValidFrom` on logout; add a same-origin check helper to mutating routes; cap
`phone`, `company`, `deliveryNotes`, `attachmentNames`, `source`; route blog preview
through `previewTokenValid()`; `encodeURIComponent` + ObjectId check in
`blog/submit/route.ts:239`; log status codes only in `email.ts`, `orders.service.ts`,
`tickets.service.ts`; plan a nonce-based CSP; derive upload `contentType` from the
sniffed kind and gate `enquiry-uploads` create on the internal key.

### Already good (website, verified with file references by the audit)
Prices, tax and quantities recomputed server-side from the CMS; Razorpay signatures and
webhooks verified in constant time with amount cross-checks and idempotency; orders,
invoices and enquiries owner-scoped behind the verified-email gate; Google OAuth with
state, PKCE, `__Host-` cookies and full id-token checks; session cookie httpOnly, Secure,
Lax, host-only; password change re-verifies and signs out other devices; forgot-password
non-enumerating and rate-limited; internal key compared in constant time with the
placeholder refused at boot; no SSRF surface (no user-supplied URL is fetched; every
user value in an internal-key URL is encoded or regex-gated); uploads sniffed, capped and
sanitised; analytics collector sanitised; headers complete with `poweredByHeader: false`;
only `.env.example` tracked; Next 15.5.25 / React 19.2.8 unaffected by the middleware
bypass and React2Shell CVEs.
